# Changelog

## 0.1.0a17 (unreleased)

**Fixed:**
- **Boiler Room sets are listened to.** Boiler Room describes nearly every upload in one line: “Mura Masa – live from Boiler Room x Cupra at Primavera Sound Barcelona.” djlib read that line as a song, so `djlib set 'LINK'` showed one made-up song after 14 seconds and never listened. A line about the set itself is not a song any more: who played where or when (“live from …”, “DJ set at …”, “recorded live at …”, “Glastonbury 2019”, the set's date), a set or show (“Kaytranada - Boiler Room Montreal”), or the uploader beside a venue. “Main Source - Live at the Barbeque” is still a song, and so is a mix in brackets such as “(Live at Alive 2007)”. Only the set's page is read this way: a tracklist you give djlib is read as you wrote it.
- **A tracklist too short for the set is listened to.** When the description names one song, or fewer than one for every 12 minutes of the set (four or fewer for an hour), `djlib set 'LINK'` says “The description names only 1 song, so djlib is listening to the set to find the rest.” and listens. With `--no-identify`, or when djlib can't listen, it uses the list and warns “The description names only 2 songs for this 57-minute set: songs may be missing.”
- **A tracklist written “Title - Artist” agrees with what Shazam heard.** Avalon Emerson's YouTube description lists “Desert Hike - Tibi Dabo”. Where Shazam heard Tibi Dabo's “Desert Hike”, that line is now the song Shazam heard, shown as “Tibi Dabo - Desert Hike”, instead of two ✗ conflicts, and its notes say “the description lists it title first”. Lines Shazam didn't hear stay as written, and so does the whole list when djlib doesn't listen.

**Upgrading:**
- **A set that showed one made-up song** (most Boiler Room uploads) is listened to when you check it again. Its songs are new, so it becomes a new set and crate; if the old one is in rekordbox, the new playlist comes in as “Name (2)”. Delete the older one.
- **For scripts and assistants:** JSON changes are additions (listed in [CONTRACT](docs/CONTRACT.md)): the `identify_started` event's `identify_reason` can be `sparse`, and a listing's evidence for a line read the other way round has `turned: true`, with the line as written in `label`. `djlib set` warns when it uses a tracklist with too few songs without listening.

## 0.1.0a16

**New:**
- **The whole set on screen.** `djlib set 'LINK'` shows every track in set order: its time, how sure djlib is, and whether you own it (✓ owned, ✗ missing, ? maybe yours, ≈ another mix you own, such as “≈ Radio Edit”, or an ID). The headline adds it up: “14 of 22 owned · 1 in another mix · 7 missing”. In a terminal that shows links, a time opens the set at that moment.
- **A shopping list for the rest.** The set ends with “Your shopping list (7)”. `djlib requests report` lists each missing song by its time, with Beatport, Bandcamp and Traxsource searches, and saves it as “<set> - to buy.txt” in the Shopping lists folder of djlib's folder (a later set with the same name adds its code, so lists never replace each other). These are store searches, not purchases: check it's the right mix before you buy.
- **`djlib set paste`.** Copy a set link or a tracklist (from 1001Tracklists, a message, or spreadsheet cells with their header row), then run `djlib set paste`. No file needed. `djlib set -` reads it from a pipe. `paste` reads the clipboard on a Mac; elsewhere `djlib set -` asks you to paste it into the terminal (end with Ctrl-D, or Ctrl-Z then Enter on Windows), and help and first steps suggest that instead.
- **Your recent Shazams first.** With more than 100 Shazams, `djlib shazam status` suggests the last 30 days (`djlib set shazam:2026-09-14`, with the right date) before your whole history, which comes oldest first, 1,000 at a time. The setup steps are rewritten for macOS 26.
- **Your sets on the review page.** `djlib ui` opens on Sets: each set as a strip of owned, missing, other mix and IDs. A set's page lists every track with its time (a link into the set), how sure djlib is and what you own, with store searches for the missing ones, and opens the set's crate with the commands that put it in rekordbox and on your USB.
- **Maybe yours.** A Shazam list has no tracklist to spell “Robert Glasper” for Shazam's “Robert Glasper Experiment”. A file with the same title and mix whose artist credit is shorter or longer (or has some of the names) now shows “? maybe yours” instead of “✗ missing”, stays off the shopping list, and counts as owned once you pick Use this on the review page. Another mix or another artist is never offered.
- **Honest listening.** While djlib listens it shows where it is in the set (“Listening… 15:30 of 42:05 · 5 songs so far”) and says when Shazam is slow (“Shazam is slow, waiting (Ctrl-C is safe)”). There is no countdown any more, because it was wrong. An hour-long set usually takes 5–10 minutes, up to half an hour when Shazam is busy. Before a long listen, `djlib set LINK` says why it is listening and how long that takes, in those words.

**Upgrading:**
- **Sets you checked keep their crate and playlist.** Checking a set again that you checked with 0.1.0a15 updates that set when its name and songs are the same, so its crate and rekordbox playlist stay. Spelling the songs another way (“ft.” for “Feat.”, other capitals) or a tracklist's new times don't count. Three cases still make a new one:
  - 0.1.0a16 finds more songs you own (Kaytranada's Boiler Room: 14 of 22, was 12). The new crate goes into rekordbox as “Name (2)”, as for any set that gained songs. Delete the older playlist if you don't need it.
  - A tracklist file, checked without `--source`, with untimed “ID - ID” lines, which 0.1.0a15 left out. It has more lines now, so it becomes a new set, crate and “(2)” playlist, even when you own the same songs.
  - Shazam sets have new names (“Shazam 26 Sep – 12 Oct”). A Shazam set checked again becomes a new set under the new name, so no “(2)”.
- **Upgrading from 0.1.0a15:** `djlib upgrade` runs 0.1.0a15's own upgrade. When that moves djlib to Python 3.12, it can end with a `ModuleNotFoundError` traceback after 0.1.0a16 is installed. The upgrade worked: run `djlib doctor` to check. From 0.1.0a16 on, the upgrade finishes in the djlib it just installed.
- **`djlib init FOLDER`** now adds the folder to an existing setup. It used to stop with `ROOTS_NOT_UPDATED`.
- **For scripts and assistants:** JSON changes are additions (listed in [CONTRACT](docs/CONTRACT.md)), except these values:
  - Next steps. `djlib identify` suggests `djlib set URL --no-rekordbox` first, then `djlib identify URL --tracklist paste`; `djlib_job` gives the same first step, then `djlib_identify_set with tracklist_text` instead of the clipboard command, and adds `next_without_shell`. `SOURCE_BROWSER_ONLY` `details.next` is `djlib set paste` from `djlib set` and `djlib identify 'LINK' --tracklist paste` from `djlib identify` (on a Mac; a FILE form elsewhere). `TRACKLIST_NOT_FOUND` `details.tracklist_next` and `SET_PREVIEW_ONLY` `details.next` are `djlib set paste --source URL`.
  - Track notes read “Shazam heard it at 05:39 (4×)”, “Shazam heard it once at 01:09”, “MixesDB spells it …” and “also in your tracklist” (it was “the tracklist file”), no longer “Shazam: 11 windows from …”. The notice about failed windows reads “Shazam couldn't answer for 3 of 62 minutes; those parts count as not heard.” and comes only from the run that listened.
  - `SHAZAM_NOTHING_NEW`'s message and the 1,000-song Shazam warning no longer contain a command: read `details.next` and `result.shazam.next_spec`. `shazam list` and `djlib_shazam_history` list the latest Shazam first.
  - `djlib_identify_set`'s `tracklist_source` defaults to `file` (it was `1001tracklists`), and repeating a key returns the same summary as `djlib_job`.
  - The MCP tools for saved sets (`djlib_request`, `djlib_refresh_request`, `djlib_resolve_request`, `djlib_request_report`, `djlib_collect_request`) and `djlib_job` and `djlib_shazam_history` describe themselves in sets, crates and songs; their names and arguments are unchanged.
  - `WORKSPACE_REQUIRED` and `SOURCE_NOT_ALLOWED` have new messages; the codes are unchanged. The terminal no longer prints error codes.
  - Messages a DJ can meet speak of sets and crates: `NOT_FOUND` reads “That set was not found.” (it was “Request list …”), an unknown or ambiguous set name says “No set matches …” or “matches 2 sets: Shazam (5bd95c9b); …” with the IDs the terminal prints, and `COLLECTION_EMPTY` and `REQUEST_STALE` say what to do in those words. `djlib rekordbox push --help` shows `CRATE...` and `--request SET`; `--revision` and `djlib init --allow-root` still work but are left out of help; `djlib ui` and the review page say “This link is private to you; it works while djlib is running.”; `djlib use`, `DISK_FULL` and a failed listen speak of djlib's folder, and a pick that no longer works says to check the set again.
  - An ID line needs only its label; a time or link is optional. A named line of a pasted or file tracklist keeps its time (`timestamp`), so those lists get new keys; a set checked again stays the same set.
  - Captured output is one line of JSON (`--json` at a terminal stays indented).
  - `GET /requests` (`requests list`, `djlib_requests`, the review page) lists sets by when they were last checked (`updated_at`, which every check moves, also one that changes nothing), not made.
  - `requests create --text` names pasted spreadsheet cells after their first song, as `djlib set` does, and reads Shazam's CSV export. `requests report`'s `shopping_list` is in `<djlib folder>/Shopping lists/`. `SOURCE_FAILED`, `SOURCE_RATE_LIMITED` and `SOURCE_AUTH_REQUIRED` have new messages.
  - `own` can be `maybe`, and a candidate's `identity_match` `similar_credits`. `RequestItem.also` takes up to three spellings. `requests get` says “pick a copy”, “file unavailable” and “to check” where it said “ambiguous” and “unavailable”, and its columns read Own, Track and Your file (they were Status, Requested and Match), with “as Robert Glasper” under the file.
  - The terminal's first-run error reads “Tell it where your music is” with `djlib init ~/Music` and `djlib scan`; doctor's first row is “Music folders”.

**Details**

*Owned or missing*
- **A song heard under other credits counts as owned under the tracklist's spelling.** Shazam says “Robert Glasper Experiment”, MixesDB and your file say “Robert Glasper”: that's owned now, in the mix that was heard. Every tracklist's spelling counts, so pasting a 1001Tracklists list that spells it as Shazam did keeps MixesDB's. Under the table the set says “Owned under another spelling: #2 Robert Glasper”, and `djlib requests get` shows “as Robert Glasper” next to the file. A mix the tracklist names but the audio didn't hear stays another mix you own and never goes in the crate.
- **“and” matches “&”** in titles (“Me Myself and I”), and a remixer's country tag inside a mix name is ignored (“(Antdot & Maz (BR) Remix)”). This is a fallback only: when you own a file spelled exactly as asked, that file is the match. “VIP”, “Dub” and a “(BR)” at the end still count.
- **A song you own twice, or on a drive that isn't plugged in, is owned but to check.** `djlib set`, `djlib status`, `djlib requests`, `djlib requests get` and the review page all say “1 of 4 owned · 1 to check”, and what it needs: “! owned, pick a copy” (status and `requests get` point to the review page's Use this) or “! owned, file unavailable”. Only songs with one readable copy go in the crate, one file each: a song a set lists twice is in its crate once, and status no longer calls that crate outdated.
- **Another mix you own reads “≈ Radio Edit”** in amber, not a red “missing”. djlib still counts only the exact mix and says so under the table.

*Tracklists you paste or type*
- `paste` and `-` work for `djlib set`, `djlib identify`, `--tracklist` and `djlib requests create --text`, which also reads spreadsheet cells and Artist/Title CSVs as `djlib set` does. A copied link is used as the link, also with words around it; anything else is read as a tracklist (up to 1 MB). Off a Mac, pipe it in with `-`.
- A paste without a heading is named “Pasted 14 Oct · <first song> + N more”, so two pastes never share a name.
- TextEdit (RTF) tracklists are converted on a Mac. UTF-16 and Windows (cp1252) files read as they are. A missing, empty, binary or folder path says what's wrong. A set link typed without https:// gets it (“Reading it as https://…”), with your other options kept. Links in quotes, curly quotes included, and links zsh pasted with backslashes (`\?`, `\=`) work.
- A Shazam CSV given as a file (`djlib set shazamlibrary.csv`) is read as your Shazams. Any other CSV or TSV with Artist and Title columns (a spreadsheet, or a Serato or rekordbox history saved as CSV) is a song list named after the file, and a Mix or Version column keeps the versions exact.
- Untimed “ID - ID” and “Artist - ID” lines stay in place, so the numbers match your list. Every line keeps its time, so a timed paste gets a Time column; a time on a line of its own, as 1001Tracklists copies it, is the next track's time.
- A pasted name is your own: a pasted list is named after the day you paste it, so the same paste on another day is a new set.
- A tracklist added to a set link (`--tracklist`) is kept for the set, and the next `--tracklist` replaces it. Its skipped label lines are said when you give it, not on every later check. A partial paste no longer doubles a song nobody heard (“Poison” twice at 26:00).
- A 1001Tracklists copy cut short (“Save 12 more tracks”) says how many tracks it hid and how to get them, and the set stays marked as a partial list: in `requests get`, the shopping list, status and the review page.
- More than 3 skipped label or heading lines read as one line in the terminal. A list cut short, unreadable lines and lines with a loose dash are still quoted one by one.
- `djlib set` and `djlib identify` with nothing after them show the ways in.
- `djlib init FOLDER…` takes folders directly, and the installer takes a folder dragged into Terminal.
- `djlib --help` now opens with “Every track in a set, checked against your music, into rekordbox and onto USB.” It and the installer's closing lines show the three ways in: `djlib set 'LINK'`, `djlib shazam status` and `djlib set paste`.

*Set links and listening*
- Track names wrap instead of being cut, and at 80 columns most tracks fit on one line. The table has a Time column when the tracklist times its songs; otherwise an ID keeps its time beside it (“ID @ 06:20”). `djlib set --help` fits 80 columns.
- Above 60 songs (a long Shazam history) the table shows the first 25 songs you don't own, then “… and N more: djlib requests report <set>”.
- Big counts have thousands separators: “0 of 1,000 owned · 1,000 missing”, “Not owned yet (1,000 of 1,000)”, “Your shopping list (1,000)”, in `djlib requests` and on the review page too.
- One name for IDs: “ID”, or “ID — maybe <song>” when djlib heard something there. `djlib identify` reads “13 tracks · 8 heard by Shazam · 3 from tracklists only · 2 IDs”, with no percentages, and lists each song heard once, not placed, by its time. A song Shazam heard in one place and again in another counts as heard twice: an ID's guess reads “Shazam heard it at 51:09 and 56:39”, not “once”, and isn't listed again as heard once.
- After `--no-rekordbox` the next step is “Put it in rekordbox” (`djlib rekordbox push <crate>`) or “Or straight onto your USB”. After `djlib identify`, the first next step checks the set against your music without making a rekordbox playlist.
- A 1001Tracklists link (also 1001.tl) says what works: copy the tracklist, then `djlib set paste`; better, the set's own YouTube or SoundCloud link with `--tracklist paste`. A Mixcloud link says Mixcloud doesn't allow downloads and what to use instead; its JSON adds `details.next_for_assistants`, as the 1001Tracklists refusal does, so an assistant never runs `paste`.
- When YouTube or SoundCloud doesn't answer, a set djlib heard before comes back from what it read and heard, saying so; other page errors say the site didn't answer, not “the provider”.
- Every line counted as an ID says “○ ID” under Sure, its guess beside its name, and the spellings a file was owned under read in one form.
- MixesDB lookups wait 4 seconds between requests, as its robots.txt asks. Sets looked up at the same time each get their answer. `DJLIB_MIXESDB=off` (or `0`, `false`, `no`) turns the lookups off for `djlib set`, `djlib identify` and assistants; they stay on by default.

*Your Shazams*
- With more than 100 Shazams and none checked yet, `djlib shazam status` suggests the last 30 days first, then your whole history. A list cut at 1,000 says which days it covers, and “The next 520 Shazams” brings the rest; status keeps offering them until they are checked.
- Without Full Disk Access, status says so (“djlib can't open your Shazam history yet”) and its next step opens the setting, instead of showing the iCloud steps.
- “Nothing new” is calm (“○ Nothing new since Mon 12 Oct 15:20”) and points to your last Shazam crate.
- Names say which days a list covers (“Shazam 26 Sep – 12 Oct”) or which file it came from (“Shazam (shazamlibrary.csv)”). Notes keep place names but not bare coordinates, and a Shazam with only a date no longer shows a made-up midnight.
- `djlib shazam list` shows the latest Shazam first, with a × column for songs you Shazamed more than once. A Shazam list reads newest first in `djlib set` and the shopping list too, as on the review page, with the day of each Shazam, and says repeats: “1,000 Shazams · 983 different songs”.
- No history? Status and `djlib set shazam` also offer Apple Music's “My Shazam Tracks” (`djlib set shazam:apple-music`) and a CSV (`djlib set ~/Downloads/shazamlibrary.csv`).

*Status, sets and crates*
- `last` is the set you checked most recently (checking one again counts) and its crate, for `djlib requests report last` and `djlib rekordbox push last`.
- `djlib status` lists your sets with their crates, one line each: “Kaytranada … 14 of 22 owned · 1 in another mix · 7 missing · crate 14 · ✓ in rekordbox · ✓ on DJ_USB 1d ago”. Each crate sits on the line of the set it was made from; others go under “Other crates”. On a computer without rekordbox, status doesn't talk about rekordbox for your crates, and while rekordbox is closed it says once that it can't tell, not “not in rekordbox yet” on each line. A set checked again shows its crate even when that crate is older than the newest five. When nothing is checked yet, it suggests `djlib set paste` and, when this Mac has Shazams, your recent ones.
- `djlib requests` lists your sets with the same counts as `djlib set`, in the same order everywhere (`djlib set`, status, `djlib requests`, `requests get`, the review page): owned, to check, maybe yours, in another mix, missing, IDs. The set you checked last comes first, also when you checked it again and nothing changed, and so on the review page. At 80 columns it keeps every count and the set's name; in a narrower window IDs, Maybe and To check go before the name gets too short, and a note says so. - `djlib library mirage` searches without `-q`. `djlib crate` alone shows your newest crate, and `djlib requests`, `djlib shazam`, `djlib roots` and `djlib jobs` alone do the obvious thing. “Did you mean” suggests only commands you can see in help.
- Before setup, djlib says “djlib isn't set up yet · Tell it where your music is” with `djlib init ~/Music` and `djlib scan` (`djlib set 'LINK'` says it at once, before reading the set); `djlib init` ends with “Ready” and your music folders. Errors in the terminal have a plain heading, no code, and list every way forward. Rescans say “✓ 22 tracks, 0 new”, counting songs as `djlib status` does (a second copy of a song is no new track), and with several music folders `djlib scan` says it once: “✓ 23 tracks in 2 folders, 0 new”, with one Next block (with a drive unplugged, it counts only the folders it scanned). A scan shows “Reading your music”. Doctor's rows read “Background service” and “YouTube helper”, and until the first `djlib rekordbox sync` it says to run that once. Status says “no BPM yet” instead of “BPM for 0”.

It says the Claude Code plugin was updated only when it reached the new release; when the plugin marketplace doesn't offer it yet, it says so.
- A copy of your djlib folder (a backup or a test copy) starts its own background service and never writes into the original. The same folder typed another way (upper or lower case on a Mac) keeps using its service.
- Songs `--fetch` downloads say “Web rip from YouTube (stream quality) — buy before playing out · <link>” in rekordbox's Comments column.

## 0.1.0a15

**Find every song in a set.**
- **`djlib identify LINK`** listens to a YouTube or SoundCloud set and tells you what was played. It reads the set's description, chapters and listener comments and looks the set up on MixesDB, listens to a 12-second window every 30 seconds (every minute when a tracklist already times the songs, which halves the requests), listens again where songs change, and merges it all into one timestamped tracklist, with live progress. How long that takes depends on Shazam: live, a 62-minute set took 7 minutes on a quiet day and over 30 after a day of heavy testing, when Shazam kept asking djlib to slow down; djlib waits instead of failing, and the progress says when it is waiting. Each track says how sure djlib is (confirmed, likely, weak, conflict or unidentified) and why, e.g. “Shazam: 11 windows from 06:00; also in the description”. An ID stays an ID, shown as “ID — likely …” with its evidence; a song heard only once is never made a track. Where nothing could be heard (a breakdown, a long blend, an outro), the song before keeps playing instead of becoming an extra ID, and the result says how much of the set was heard as well as how much was named. When the audio and a tracklist spell a song differently (“Armand Val Helden” on MixesDB), the audio's spelling is kept and the other is noted, so a typo doesn't make a song you own look missing. The tracklist is saved, and `djlib set FILE` reads it.
- **`djlib set LINK` listens when it needs to**: when the set's tracklist is missing or has IDs. `--no-identify` uses the published list only, `--identify` always listens. Without song recognition it still uses the published list and says why. The result gains `identified` (how much of the set was named), and each missing song says why it is in the set.
- **MixesDB is checked automatically.** A set link without a tracklist in its description gets MixesDB's, when MixesDB has a page that is surely that set (it links the same upload, or names the same DJs and event with the same day or length). `djlib set LINK` uses it as the set's tracklist, also with `--no-identify` or without song recognition, and listens only when MixesDB doesn't call it complete or it has IDs; `djlib identify` merges it with what it hears. Both say “Tracklist from MixesDB: …” with the page's link, so you can check it. A doubtful page, an outage or a slow answer means no MixesDB tracklist, never an error.
- **Add a tracklist from 1001Tracklists** with `--tracklist FILE` on `identify` or `set`: djlib merges it with what it hears and remembers it for the set. djlib still doesn't fetch 1001Tracklists itself; your assistant can read it in your browser.
- **Stop and carry on.** Ctrl-C stops listening and keeps the download and what was heard, and running the same command again continues from there; so does a retry after the recognition service turned requests away. A set identified before comes back at once, also while another set is being listened to; `--again` listens again and keeps the earlier tracklist until the new one is made. A SoundCloud set that only plays a preview says so. A listen the recognizer refuses, or that fails on most of the set, stops with an error you can retry (`RECOGNITION_FAILING`) instead of an empty tracklist, and a disk without room for the set says so before downloading (`DISK_FULL`).
- **Shazam by default, licensed if you prefer.** djlib uses Shazam's recognition service the way the Shazam app does. Apple doesn't offer it to other apps, so it may slow down or stop working, and your first identification says so once. `DJLIB_RECOGNIZER=audd` with `DJLIB_AUDD_TOKEN`, or `DJLIB_RECOGNIZER=acrcloud` with `DJLIB_ACRCLOUD_HOST`, `DJLIB_ACRCLOUD_KEY` and `DJLIB_ACRCLOUD_SECRET`, use a licensed service with your own account; `--recognizer` picks one for a run. `djlib doctor` shows which one is used and what is missing.
- **Installed with djlib.** The installer and `djlib upgrade` now install song recognition (the `recognize` extra) on Python 3.12, where it has ready-made macOS and Windows packages. 0.1.0a14's `djlib upgrade` installs this release without it; run `djlib upgrade` once more and it adds it, or run the install line again.
- **Descriptions that time only their IDs** keep their other tracks too, also for `djlib set LINK` without listening.
