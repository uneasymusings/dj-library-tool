# Version-one command contract

This document describes the CLI, the authenticated local HTTP routes and 45 MCP tools. `djlib mcp serve` exposes 22 core tools by default (tracklists, request lists, crates, set links and their identification, Shazam history, web sources, downloads, jobs and their control, and rekordbox analysis) and all 45 with `DJLIB_MCP_TOOLS=full`; `djlib.interfaces.tool_manifest` lists both. rekordbox and USB steps (`set`, `rekordbox push|usb|pull`) are CLI-only. The response envelope is schema version `1`. See [status](STATUS.md) for validation and publication evidence.

## Envelope

All application results use:

```json
{
  "schema_version": "1",
  "ok": true,
  "request_id": "req_unique-id",
  "result": {},
  "warnings": [],
  "error": null
}
```

Failures set `ok: false`, `result: null`, and `error: {code, message, retryable}`, plus `details` where a code has them; `details.next` (with an optional `next_label`) is the one command that helps, which the terminal shows unbroken under the message. Since 0.1.0a16, `details` may also carry `title` (a short heading the terminal shows in place of the code) and `next_steps` (`[{label, command, note?}]`, more than one way forward; `next`/`next_label` stay its first step, and `note` is printed muted under its command). The terminal no longer prints error codes; JSON keeps them. `SOURCE_NOT_ALLOWED` adds `details.path` (the folder to allow with `djlib roots add`), and it and `WORKSPACE_REQUIRED` have new messages (“PATH is outside your music folders.”, “There is no djlib workspace in ROOT yet.”). Request IDs identify calls; job IDs identify accepted work. `warnings` lists plain-language notes that did not stop the command (skipped tracklist lines, a published list used instead of listening, one-time notices); HTTP routes leave it empty. Quality evidence appears in asset properties/manifests; an empty warnings array is not a quality guarantee.

CLI stdout is this JSON envelope whenever output is captured (pipes, files, assistants, CI), with the global `--json` flag (accepted before or after the subcommand), or with `DJLIB_OUTPUT=json`. In an interactive terminal, commands print readable views instead: tables, live job progress on stderr and copy-pasteable next steps; errors go to stderr. `DJLIB_OUTPUT=pretty` forces the terminal view. Presentation never changes what a command submits, and generated assistant sessions set `DJLIB_OUTPUT=json`. Help and argument parsing follow Typer conventions.

Interactive terminals add conveniences that scripts never get implicitly: `--key` may be omitted for `scan`, `start`, `export` and `delivery prepare` (a fresh key is generated; with JSON output a missing key is an `INPUT_INVALID` envelope), submissions follow their job until it finishes (Ctrl-C detaches; the job keeps running), and `delivery observe ID` without `--file` asks what you saw and fills counts and recording IDs from the frozen, checksummed manifest only after you confirm. `scan` without a path uses the only allowed root, in either mode. MCP stdout is protocol-only; each tool's text content is the compact JSON of its `structuredContent` envelope, and before `djlib init` every tool answers `WORKSPACE_REQUIRED`. Workspace service diagnostics go to `runtime/service.log`. The service has no unauthenticated browser UI or public endpoint.

## Inputs

Requests are Pydantic contracts with unknown fields rejected. `djlib schemas` emits current machine-readable JSON Schemas without starting the service. The checked-in [schema artifact](../schemas/inputs.json) is generated from the same classes.

| Contract | Purpose |
| --- | --- |
| `CollectionRequest` | Name, profile, explicit local tracks with path/artist/title/version. |
| `StartRequest` | Existing plan ID, revision, submission key. |
| `DownloadRequest` | Name, selected source tracks with URL/artist/title/version and up to three `alternates` (other uploads of the same recording), submission key. |
| `IdentifyRequest` | One YouTube or SoundCloud set `url`, up to five `tracklists` (`source`, `text`), optional `recognizer` (`shazam`, `audd`, `acrcloud`), `again`, optional `name`, submission key. |
| `ScanRequest` | Allowed directory, submission key. |
| `ResolveRequest` | Current review revision and chosen resolution. |
| `ExportRequest` | Collection ID and submission key. |
| `DeviceRequest` | Mounted path and estimated bytes needed; read-only effect. |
| `DeliveryRequest` | Name, existing collection IDs, workflow, app version, target profile, audio mode, and pilot/full selection. |
| `DeliveryPrepareRequest` | Current delivery revision and preparation submission key. |
| `DeliveryDeviceRequest` | Current delivery revision and exact mounted volume path to bind read-only. |
| `DeliveryObservation` | Current revision, observed stage, app version, track/playlist coverage, checked recording IDs, observer, notes, method, outcome, and optional actual hardware details. |
| `DeliveryVerifyRequest` | Current delivery revision for working-file verification or audio-hash readback on the bound volume. |
| `DeliveryNativeXMLRequest` | Current delivery revision and allowed native rekordbox XML path; read-only snapshot comparison. |
| `RequestCreate` | Stable key, list name and up to 1,000 exact named requests (each with at most one `also` spelling of its credits) or unknown IDs (a label; time and link are optional evidence). |
| `RequestRefresh` | Current request revision and optional selected item IDs for bounded file checks. |
| `RequestResolution` | Current revision and explicit source, catalog identity selection or clear action. |
| `AnnotationRequest` | Exact recording/byte revision, annotation revision, stable key and supplied field patch. |
| `OrganizationRequest` | Stable key, explicit catalog references, filters, unknown policy and ordering. |
| `RootsRequest` | One to 100 existing directory paths, explicitly added to allowed roots. |
| `ReconcileRequest` | Stable key and up to 1,000 distinct changed paths, each pinning an old revision, current new SHA-256 and `tag_only` or `replace_audio` action. |

Labels reject control characters and blank artist/title. Named identity normalizes Unicode/case/spacing while retaining versions and symbol-only distinctions. A mix name written inside the title is equivalent to the same name in the version field: “Rain (Extended Mix)” with no version matches title “Rain” plus version “Extended Mix” (`identity_match: equivalent_labels` in request candidates). Since 0.1.0a16 request matching also folds “and” with “&” in titles and drops a two- or three-capital-letter country tag inside a mix name when more words follow it (“(Antdot & Maz (BR) Remix)” matches “(Antdot & Maz Remix)”); “VIP”, “DUB”, “MIX”, “RMX” and a trailing “(XX)” are kept. These folds are a fallback: when any candidate is identical or equivalent without them, only those are hash-checked and can satisfy the item, and a candidate that matches only through a fold stays listed as `equivalent_labels` with `availability: not_checked` (still selectable with `requests resolve`). `contracts.label_form`, `credit_form` and `equivalent_labels` take `fold=False` for the 0.1.0a15 comparison. The same folds merge duplicate Shazams and apply to download label checks. Identical bytes cataloged under equivalent labels reuse that recording instead of failing with `EXISTING_IDENTITY_CONFLICT`; a different version still conflicts. A download joins the recording its labels name as request matching compares them (“Lasso” and “Lasso (Original Mix)”, “Antdot & Maz (BR)” and “Maz, Antdot”); when that recording already has a managed file with the same decoded audio (`audio_payload`), the download reuses it (`reused: true`) instead of storing a second copy. Another mix or a live take stays its own recording, and scans keep each file's own labels. Stored identity keys are unchanged. Incomplete-label scans use provisional byte identity; WAV artist/title come from ID3 or, when absent, the RIFF INFO chunk. Scans skip djlib's own workspace folders and links that resolve outside allowed roots, and report the counts in the scan job's `result.skipped_files`. These are conservative catalog rules, not an acoustic identity resolver or automatic repair of historical merges. Input errors identify invalid field locations and generic reasons without echoing submitted values.

### Delivery inputs

`DeliveryRequest` accepts 1–100 distinct `collection_ids` and freezes their accepted recording IDs, byte revisions, labels, and membership. Repeated recordings are prepared once while retaining each collection's membership. Different byte revisions for the same recording return `DELIVERY_REVISION_CONFLICT`; delivery does not silently select one. The combined selection is limited to 10,000 unique recordings.

- `workflow`: `rekordbox_import`, `serato_import`, `rekordbox_usb` or `serato_portable`.
- `app_version`: required. `hardware_profile` is required only for `rekordbox_usb` and must be returned by `delivery targets`; the other workflows reject that field. App-only import/analysis needs no USB or player/controller model.
- `audio_mode`: `preserve` (default), `mp3_320`, or `wav16_44100`. Preparation always creates separate working copies; conversion does not improve source fidelity.
- `phase`: `pilot` (default) or `full`. `pilot_size` is 1–5, default 3; sampling visits the selected collections in round-robin order.
- Full local preparation may omit `pilot_delivery_id`, explicitly reporting unvalidated local preparation. If supplied, the pilot must be completed and match workflow, hardware profile, audio mode and app version; otherwise preparation returns `PILOT_REQUIRED`. All native/device readiness gates remain. Full copies do not inherit native cues or analysis from separate pilot paths.

`DeliveryObservation.stage` is one of `imported`, `analyzed`, `native_exported`, `device_library_checked`, or `hardware_playback`. Passed observations require preceding stages, the planned app version, exact unique-track and per-collection counts, and every checked recording ID. Only hardware playback for a full delivery permits a nonempty sample; a pilot requires playback of every selected recording. `playlist_counts` uses collection IDs as keys. Failed observations may report incomplete or zero coverage and invalidate later observations.

`method` is `native_app_ui` for the first four stages and `physical_hardware` for playback. `outcome` is `passed` or `failed`; `observer` and `notes` are required. These observations remain operator-reported evidence. Passed rekordbox hardware playback additionally requires matching `hardware_profile`, nonblank `firmware_version`, and `storage_recognized: true`; missing details return `HARDWARE_DETAILS_REQUIRED`. CDJ-3000 firmware 3.30, including normalized whitespace/`v` prefixes, returns `FIRMWARE_UNSUPPORTED`.

App-only workflows accept only `imported` and `analyzed` observations, followed by `verify-app`. Successful verification jobs return an evidence-commit receipt. Read delivery status for `app_requirements_met_at_last_check` and `evidence.app_readback.checked_at`; these retain historical, operator-conditional evidence and never assert fresh app/USB readiness. USB workflows require their device/native/hardware stages and fresh `verify-device`. A native XML inspection checks a rekordbox snapshot without changing any stage or readiness; the input path must be authorized, and product-version mismatches remain explicit.

### Request and organization inputs

`requests create --text FILE` builds a `RequestCreate` from a plain tracklist in the CLI: one `Artist - Title (Mix)` per line, with numbering, bullets, timestamps and a trailing `[LABEL]` removed (a bracketed mix name is kept). `ID - ID` and `Artist - ID` lines become unknown items in their place, labelled as written, with or without a timestamp or `--source` URL (0.1.0a15 dropped untimed ones). A line holding only a time (`01:09`, `[01:09]`) is the time of the next line that becomes an item. Leading unnumbered lines of a numbered list are headings; the first names the list, except a heading starting with `{\` (RTF), which is skipped with reason `tracklists.RICH_TEXT`. Files are decoded as UTF-8 (with or without a BOM), then UTF-16 with a BOM, then cp1252; RTF is converted with macOS `textutil` and is `INPUT_INVALID` elsewhere; an empty, binary, missing or folder path is `INPUT_INVALID` with `details.title`. In place of FILE, `paste` reads the clipboard (macOS `pbpaste`; `INPUT_INVALID` elsewhere) and `-` reads stdin; an untitled pasted or piped tracklist is named `Pasted <D Mon> · <first song> + N more`, and text that is only the set's link raises `INPUT_INVALID` (titled “Copy the tracklist too”, or “That's the set's link” for stdin). `set`, `identify` and `--tracklist` accept `paste` and `-` the same way; for `set` and `identify` a single http(s) link in the text, with no song named, is used as the link. Arguments wrapped in one pair of straight or curly quotes are unquoted unless a file has that literal name. `set` and `identify` without an argument return `INPUT_INVALID` (exit 2) whose `next_steps` list the ways in. Lines that are skipped are reported in the envelope's `warnings`; the terminal folds more than three label or heading skips into one line and still quotes the others.

Since 0.1.0a16 `requests report` in the CLI (a shopping list in the terminal) adds to the report's result `name`, `to_buy` (`[{position, timestamp, label, shop}]`), `other_mixes` (`[{position, timestamp, label, title, you_own, shop}]`), `ids` (`[{position, timestamp}]`) and `shopping_list`, the path of `<set> - to buy.txt` written beside the report and replaced on each run (null when it couldn't be written); `report_path` and the report file are unchanged. `djlib_request_report` and `POST /requests/{id}/report` are unchanged.

`RequestCollect` (`revision`, optional `name`) queues an `organize` job over the request's `satisfied` items in list order, deduplicated by byte revision; nothing else is included and an empty selection is `COLLECTION_EMPTY`. Request candidates may include up to five `different_version` recordings of the same song (same artist and base title) for context; they never satisfy, disambiguate or truncate a match.

`AnalysisImport` (`path`) reads a rekordbox Collection XML export from an allowed folder or the workspace (the CLI copies the chosen file into the workspace first). Tracks match only by exact file location: catalog originals or prepared delivery working copies. Known `AverageBpm`/`Tonality` values are stored as BPM/key annotations with `source: "rekordbox_analysis"` and `verified: false`; values with any other source are kept. Library rows and collection pages include `dj: {bpm, key, bpm_source, key_source, energy, set_role}` from saved annotations.

`rekordbox push` runs in the CLI process, which macOS lets drive another app once the terminal is allowed under Accessibility; the coordinator never automates UI. For each collection it exports (hash-checked) and copies the M3U8 to `exports/rekordbox/<collection name>.m3u8` (only characters illegal in file names are replaced; rekordbox names the playlist after the file), skips names already listed in rekordbox, and chooses the file in File > Import > Import Playlist. A listed name counts as this crate only when `exports/rekordbox/history.json` records that djlib pushed this collection under it; otherwise one XML export must show the same tracks in the same order, else `APP_PLAYLIST_NAME_TAKEN` is returned before any import. Presence is confirmed by reading rekordbox's Track > Add To Playlist menu without focusing it. `--verify` performs one File > Export Collection in xml format and adds `entries/expected/matched/analyzed` per crate; `--when-idle S` waits until there has been no keyboard or mouse input for S seconds; `--request ID` first queues `requests collect`. The result lists `crates` (`collection_id`, `playlist`, `status: imported|already_in_rekordbox`, `playlist_found`), `rekordbox_ui_seconds`, `analysis_sync`, `verified_by` and `database_modified_directly: false`. Dialogs are driven through accessibility values and named buttons; the two shortcut keystrokes are sent only after confirming rekordbox is frontmost and the expected dialog has focus, otherwise the dialog is cancelled with `APP_DIALOG_FAILED`. Missing permission returns `APP_AUTOMATION_NOT_ALLOWED`; non-macOS returns `APP_AUTOMATION_UNSUPPORTED`.

`rekordbox usb` exports one collection to a mounted USB through rekordbox. Without `--device` it uses the single external, writable, non-disk-image volume (preferring one with `PIONEER/`), else `DEVICE_REQUIRED`. It pushes the playlist if rekordbox lacks it, then waits up to `--timeout` seconds (also while the screen is locked) for the user to select a playlist: whenever rekordbox is frontmost and enables Playlist > Export Playlist > *device*, the selected name is read from the prefilled Save As field of Playlist > Export a playlist to a file (*.m3u8), which is then cancelled. After a different playlist is read, the selection is read again only once the keyboard or mouse has been used since (and at most every 2 s), so the dialog does not flash while the user browses. Only when it equals the collection's playlist name does djlib click Playlist > Export Playlist > *device*; otherwise `APP_SELECTION_TIMEOUT` and nothing is exported. It waits until `PIONEER/rekordbox/export.pdb`/`exportLibrary.db` changed and stayed unchanged for one more check with no rekordbox dialog open, then reads the playlist from `PIONEER/rekordbox/export.pdb` (the device library players load; read-only DeviceSQL parsing of the track, key, artist, playlist-tree and playlist-entry tables) and checks that its entries, in order, point to files whose size and SHA-256 match the frozen manifest. If the device library or playlist cannot be read, it falls back to hashing same-size audio under `Contents/` (`verified_by: usb_file_hashes`, `playlist_on_device: false`). The result lists `playlist`, `device`, `library_updated`, `export_seconds`, `expected`, `found`, `missing` (up to 20 labels), `playlist_on_device`, `device_entries`, `in_order`, `matched_by`, `verified_by: device_library_and_file_hashes`, `player_playback_verified: false` and `database_modified_directly: false`. For verified entries, the device library's BPM and key are written to a Collection XML keyed by the original file paths and imported like `rekordbox pull` (`rekordbox_analysis`, unverified, never replacing other sources); `analysis_from_device` reports `matched`, `updated` and `kept_your_values`, or null. A locked screen otherwise returns `APP_SCREEN_LOCKED`.

`set` also accepts a YouTube or SoundCloud set URL: `POST /sources/inspect` with `comments: 1000` and `mixesdb: true` returns its description, chapters and listener comments (`text`, SoundCloud `start_time` in seconds, `like_count`, `author`); chapters (3 or more, unless none reads as a track, as with chapters YouTube names itself) or tracklist-like description lines become the tracklist, named after the upload. When they list none, `result.mixesdb` is the set's MixesDB lookup (`page_title`, `page_url`, `text` as numbered `[mm:ss] Artist - Title` lines, `complete`, `tracklist` `complete`|`incomplete`|`unknown`, `tracks`, `duration_seconds`, `players`, `match` `{by: url|title_date|title_duration|title, score}`) or null, and its text is the tracklist; with a tracklist on the page, or without `mixesdb: true`, MixesDB is not asked (`mixesdb` is null or absent). A MixesDB page counts only when it links the same upload (and the upload is not one part of a longer set), or its title names the same DJs and most of the event words and its day or length agrees (a radio show's episode needs the day); two pages that fit alike count as none. A lookup makes at most 4 requests to MixesDB's MediaWiki API, started at least 4 seconds apart across every lookup in the process (its robots.txt `Crawl-delay: 4`), with 20 seconds of asking per lookup (waiting for a turn doesn't count against it; the CLI allows 60 extra seconds on `POST /sources/inspect` with `mixesdb: true`), and an outage, rate limit or slow answer is null, never an error. When the tracklist text is empty or parses to any unknown/ID line, or comes from MixesDB without `complete`, or a finished identification of the set exists, `set` submits `POST /identifications` (below) and follows the job; `--identify` and `--tracklist FILE` (repeatable) always do, and `--no-identify` never does. The request list then comes from the identified tracklist in set order (IDs stay unknown items labelled “ID”, with their likely song only in `notes`; every item carries the track's status as `confidence`), named after `--name`, the upload title or the file heading, with the key `identified:<digest>`, and the result gains `identified` (`coverage` with `seconds_identified`, `duration_seconds`, `percent`, `seconds_heard`, `percent_heard`; `counts`, which since 0.1.0a16 adds `heard`, `listed_only` and `ids`; `tracklist_file`; `job_id`; `reused`; since 0.1.0a16 `recognizer` and `listened_at`, the time of the listen even when the result is reused); `missing[]` items carry the track's `notes` and `confidence`, and `owned_to_check[]` lists owned songs in the crate whose `confidence` is not `confirmed`. `result.mixesdb` is null, or the MixesDB page whose tracklist the set used (`page_title`, `page_url`, `tracklist`, `match`; from the identification's sources when djlib listened), and a MixesDB tracklist used without listening that is not `complete` adds a warning. When an identification `set` chose by itself fails, a published tracklist (the page's or MixesDB's) is used instead with a warning naming the cause and `listen_fix` holding the command that fixes it; without one, missing or unconfigured recognition (`DEPENDENCY_REQUIRED`, `RECOGNIZER_NOT_CONFIGURED`) becomes `TRACKLIST_NOT_FOUND` whose message starts with why djlib couldn't listen, with the fix in `details.next` and `djlib set paste --source URL` in `details.tracklist_next` (`djlib set FILE --source URL` before 0.1.0a16; without a fix, `details.next` is that command), and other errors are returned. With `--identify` or `--tracklist`, the error is always returned. Before a listen it chose, `set` prints a short notice saying why it listens, and with JSON output the `identify_started` stderr event carries `identify_reason` (`asked`, `no_tracklist`, `incomplete`, `ids` or `identified_before`). 1001Tracklists URLs (`1001tracklists.com`, `1001.tl`) return `SOURCE_BROWSER_ONLY` with `details.next` `djlib set paste` on macOS (`djlib set FILE` elsewhere), `next_label`, `next_steps` (the second is `djlib set 'LINK' --tracklist paste` with a `note`, or `--tracklist FILE` off macOS) and `next_for_assistants` (pipe the text into `djlib set 'LINK' --tracklist -` or `djlib set -`; never run `paste`, which reads the user's clipboard). Mixcloud URLs return `SOURCE_UNSUPPORTED` with a message naming the same alternatives. With a file, `--identify` or `--tracklist` require `--source URL` (else `INPUT_INVALID`) and merge the file as a listing; by default a file merges only with a finished identification of `--source`. `--tracklist` with `--no-identify`, or `--identify`/`--tracklist` with `shazam`, is `INPUT_INVALID`. `id_hints` lists, per unknown item with a timestamp, up to three identities named in comments near that time (`label`, `mentions`, `likes`, `evidence`), leaving out those whose artist or title is the title of the song just before or after the ID; they never change the request. With `--fetch`, each `missing` named item is searched through `POST /sources/search`; only candidates marked `confident` are offered, and they are downloaded (after confirmation in a terminal, or with `--yes`) by one `POST /downloads` job named “NAME — downloads” using the requested artist/title/version, after which the request is refreshed. Since 0.1.0a16 the library copy (not the original in `incoming/`) also gets a comment (ID3 `COMM`, replacing any other, or a FLAC `comment`) reading `Web rip from <site> (stream quality) — buy before playing out · <source URL>`, which rekordbox shows in its Comments column. Each chosen song carries up to three `alternates`: other uploads of the requested version that are the artist's or label's own or within two seconds of the chosen one's length. The worker tries them in order when an upload turns out to be gone (`SOURCE_UNAVAILABLE`, `SOURCE_AUTH_REQUIRED` or `DOWNLOAD_UNAVAILABLE`); each download item's result names the `source_url` that arrived and every one in `tried_urls`. Failed downloads are retried once only when a failure is `retryable`. `fetched` reports `chosen` (with each `source` and `alternates`), `needs_your_pick` (best three `options` or a `reason`), `downloaded`, `failed` and `job_id`.

`POST /sources/search` (`artist`, `title`, `version`, `limit` ≤ 20) runs YouTube and SoundCloud searches (metadata only) and returns `candidates` ranked by `source_matching.rank_sources`, each with `provider`, `url`, `title`, `uploader`, `artists` (SoundCloud's artist credit, which counts as naming the artist), `duration`, `view_count`, `score`, `confident`, `reasons`, `other_version` and `available`, plus `unavailable_providers`. The best three candidates of the requested version are then probed at once (yt-dlp picks the audio without downloading, 30 seconds at most): removed, region-locked, DRM-protected or sign-in-only uploads leave `candidates` for `unavailable` (`url`, `title`, `uploader`, `reason`), the rest are ranked again, and only a candidate whose probe passed (`available: true`) can be `confident`. A label upload within two seconds of the artist's own upload (even one that is gone) counts as that recording. Web downloads are MP3 (VBR V0, copied when already MP3) with receipts marking `source_quality: unverified`. A download job's collection is created when its first song arrives (`result.collection_id` is null until then, and stays null when every song fails); download jobs with the same name, such as repeated `set --fetch` runs of one set, add to one collection. The catalog upgrade removes the empty crates that releases before 0.1.0a14 made for downloads where nothing arrived: only a crate a download job made, with no songs, that nothing else names (that job's `result.collection_id` becomes null). The catalog is backed up first.

### Set identification

`POST /identifications` takes an `IdentifyRequest` and queues an `identify` job. Only YouTube and SoundCloud links are accepted, reduced to one canonical form (`https://www.youtube.com/watch?v=ID`, with `youtu.be`, `/live/ID` and `/embed/ID` accepted and `&t=`/`&list=` dropped; SoundCloud links without tracking parameters; an `on.soundcloud.com` short link is first resolved to the link it stands for, which must be on soundcloud.com). 1001Tracklists links (`1001tracklists.com`, `1001.tl`) return `SOURCE_BROWSER_ONLY` with the `browser_only_details` of `djlib.sources.web`: `details.next` is `djlib identify 'LINK' --tracklist paste` on macOS (`--tracklist FILE` elsewhere), then `djlib set paste` (`djlib set FILE`) in `next_steps`, plus `next_for_assistants`. Mixcloud links return `SOURCE_UNSUPPORTED` saying Mixcloud doesn't allow downloads and to use the same set's YouTube or SoundCloud link or its copied tracklist; other sites `SOURCE_UNSUPPORTED`, and playlist or channel pages `SINGLE_SOURCE_REQUIRED`. Through MCP, `djlib_identify_set` and `djlib_source_inspect` replace those details for 1001Tracklists and Mixcloud links with only `{"next": <the tool route>}` (`djlib_identify_set with the set's YouTube or SoundCloud link and tracklist_text`; for Mixcloud, that or `djlib_create_request` with its copied tracklist); codes are unchanged, and `djlib_source_inspect` answers a 1001Tracklists link with `SOURCE_UNSUPPORTED`. Unless a finished identification of the set exists and `again` is false, the request is checked before it is queued: a missing recognizer package or FFmpeg/ffprobe or yt-dlp returns `DEPENDENCY_REQUIRED`, a licensed recognizer without its keys `RECOGNIZER_NOT_CONFIGURED` (whose message says the service reads its settings when it starts: `djlib service stop`). Tracklist `source` is `1001tracklists`, `mixesdb`, `comments` or `file`, and anything else counts as `file` (the CLI names a file `1001tracklists` or `mixesdb` when its name or text says so) and `text` is at most 200,000 characters. The reply is the job; the same key with the same body returns the same job, and `request.name` is the given name or the URL. Pause, cancel, resume and retry go through `POST /jobs/{id}/control` and stop the work within about half a second, also mid-download.

Identifications run in a runner beside the worker, so scans and downloads continue meanwhile; a restart resumes the job. Listens run one at a time; a job that only shows a set identified before (no `again`, a finished result) runs in a second lane, so it never waits for another set's listen, and one job at a time works on each set. A job queued behind another identification has `result.progress` `{phase: "queued", ahead}`. While running, `result.progress` holds `phase` (`reading_page`, `downloading`, `listening`, `checking_gaps`, `merging`), `windows_done`, `windows_total`, `songs_heard`, `eta_seconds` (null until three windows were heard in this attempt, and null while `waiting` is set), since 0.1.0a16 `position_seconds` (how far the first listen got in the set's own time: windows done × stride, capped at the set's length, the whole length when done; null outside the `listening` phase), `duration_seconds` (the downloaded set's length, or null) and `waited_seconds` (how long the recognizer has kept this attempt waiting), while downloading `downloaded_bytes`, and while the recognizer makes djlib wait `waiting` (`service`, `reason` `rate_limited`|`unreachable`, `retry_in` seconds, `gives_up_in` seconds or null), until the next window is heard. The terminal shows this as “Listening… 15:30 of 42:05 · 5 songs so far” (or “34 of 124 parts” without a length) and, while `waiting` is set, “Shazam is slow, waiting (Ctrl-C is safe)” (“isn't answering” when Shazam can't be reached), with no time-left estimate. `GET /jobs/{id}` (and `djlib_job`) set `next_poll_after_seconds` to 15 for an identify job in the `reading_page`, `downloading`, `listening` or `checking_gaps` phase, 30 while `waiting` is set, 15 while queued behind another set's listen, and 2 otherwise. Events are `accepted`, `started`, `phase` per phase, then `completed` (`tracks`, `reused`) or `failed` (`code`); a restart adds `recovered`. The runner reads the page (a page `POST /sources/inspect` read with 1,000 or more comments in the last 15 minutes is reused, and so is `page.json` when this job read it before or it is under an hour old; when the comments time out the page is read without them and a notice says so) and looks the set up on MixesDB as above (an answer from the last 15 minutes is reused; the answer is kept in the set's `page.json` with `mixesdb_checked_at`, and a failed lookup is not kept), checks the disk has room for the audio and its decoding (about 56 kB per second of set plus 200 MB, else `DISK_FULL`), downloads the audio, recognizes a 12-second window every 30 seconds, or every minute when a given or published tracklist names five or more songs and times most of its lines (`result.stride` while running; Shazam paced at `DJLIB_SHAZAM_INTERVAL`, default 1 s, backing off on rate limits for up to about 15 minutes), spends up to half as many windows again where neighbouring windows disagree or failed, and merges the windows with the given tracklists, the description, the chapters (chapters repeating the description are dropped) and MixesDB's tracklist (left out when a given tracklist's `source` is `mixesdb`). A window between two regular windows can place a song change or fill a failed window but never counts towards how often a song was heard.

Text from the page, comments and MixesDB has its control characters (but newlines and tabs) and direction marks removed; a listing is read up to 400 tracks (the rest is a skipped line). On success `job.result` holds `source` (`url`, `provider`, `title`, `uploader`, `duration_seconds`), `recognizer` (`name`, `licensed`), `tracklist` (`tracks`, `coverage`, `sources`, `unplaced`; the `mixesdb` source adds `page_title`, `page_url`, `tracklist` and `match`), `counts` (`confirmed`, `likely`, `weak`, `conflict`, `unidentified`), `tracklist_file`, `tracklist_json`, `reused`, `notices`, `skipped_lines` (up to 50 `{source, line, text, reason}`; headings, and chapters or descriptions without one track, left out) and `identified_at`, with outcome `complete`. A track is `confirmed` only when the audio bears it out (heard, in one window or more, where a listing names it, or heard in three or more windows); listings alone never confirm a song, however many name it, since they copy each other (a MixesDB page often repeats the upload's description). It is `likely` with one good source (listed but not heard, two windows, or listed and heard under another name such as a remix heard as its sample; for an ID, a song heard there in two or more windows), `weak` when only listener comments or a single window name it, `conflict` when a listing names one song where three or more windows heard another, and `unidentified` for an ID nothing named. A song heard in one window never becomes a track: it can only be an ID's candidate or go to `unplaced`. A listed track keeps the listing's label unless two or more windows heard the same title with the same credited names spelt differently, when it takes the heard label; a track heard and listed under different names has `also_named` (`source`, `label`, and `provider` for the audio's; since 0.1.0a16 a listing's spelling, `source` not `audio`, also carries `artist`, `title` and `version`) and its notes give the other spelling (“MixesDB spells it …”). Notes say where the audio heard a song in set time, one phrase per recognizer: “Shazam heard it at 05:39 (4×)”, “Shazam heard it once at 01:09”, “possibly X (Shazam heard it once at 50:09)” (0.1.0a15 wrote “Shazam: N windows from …”). A track for a stretch nobody heard or listed that is at least twice the set's median song length has `songs_estimate`. Listener comments add candidates to IDs only, never a song already in the tracklist nor one whose artist or title is the title of the song just before or after the ID (listeners swap them and misspell names). `coverage.percent` counts named tracks only; `tracklist.coverage.seconds_heard` counts the seconds where the audio heard the song placed there (an ID's likely song included), and `gaps` lists the stretches of 90 seconds or more where it heard none, whatever a listing names there. A set identified with another recognizer is reused with a notice; the first identification that uses Shazam in a workspace adds the unofficial-service notice. A download shorter than 97% of the page's length is listened to with the page's length as the set's, so the rest shows as a gap, and a notice says how much was missing; windows recognition failed on are counted once in `sources[].errors`, and the run that listened (not a reused result) adds the notice “Shazam couldn't answer for N of M minutes; those parts count as not heard.” A reused identification (`reused: true`) takes a page `POST /sources/inspect` read in the last 15 minutes, reads a `page.json` older than a day again (keeping it when that fails), and asks MixesDB again when it had no answer or found no page over a day ago. Failures set `result.error` (`code`, `message`, `retryable`, `details`): `RECOGNITION_RATE_LIMITED`, `RECOGNITION_UNAVAILABLE`, `RECOGNITION_FAILING` (ten windows in a row, or more than a quarter of the set, failed: `details.windows_failed`, `windows`), `RECOGNIZER_REJECTED` (Shazam answering 401/403/404, or a licensed service refusing the key) and `DISK_FULL` add that what was heard is saved (`details.windows_heard`, `resumes: true`) and a new submission continues from there, asking failed windows again; `RECOGNIZER_NOT_CONFIGURED` adds that the service reads its settings when it starts (`djlib service stop`); `SET_PREVIEW_ONLY` means less than half of a page duration of two minutes or more could be downloaded (`details.heard_seconds`, `set_seconds`, and `next`, the `djlib set paste --source URL` command; `djlib set FILE --source URL` before 0.1.0a16). Messages speak of parts of the set, not windows (“Shazam couldn't hear 4 of 93 parts of the set …”); the details keys are unchanged. An unexpected failure is `JOB_FAILED`, or `DISK_FULL` when the disk filled up. After an `again` request fails, the message adds that the earlier tracklist is kept.

Each set has a folder `<workspace>/sets/<first 16 hex of sha256(canonical url)>/` (scans skip `sets/`): `page.json` (description, chapters, comments), `listings.json` (given tracklists; a request with tracklists replaces them, one without keeps them), `probes.jsonl` (one line per window: `at`, `window`, `match`, `error`, `pass` `scan` or `refine`, `recognizer`), `tracklist.json` (`complete`, `source`, `recognizer`, `duration`, `window`, `created_at`, `tracklist`), `tracklist.txt` (a heading, then `[mm:ss] Artist - Title (Mix)` or `[mm:ss] ID - ID` lines, for `djlib set FILE`) `previous/` (the result an `again` request replaces, until its listen finishes; meanwhile it counts as the set's identification and a request without `again` puts it back), and `audio/` (the set as published and, while it is listened to, `<name>.pcm`, the same audio decoded to 16 kHz mono; `fetching.json` while it downloads), deleted after success or a failure no retry can fix (not `retryable`), kept after a pause, cancellation, restart or retryable failure so the next run continues, and deleted by the runner once no queued or running identification needs it and nothing used it for a day; an unexpected failure deletes only the `.pcm`. `DJLIB_KEEP_SET_AUDIO` set to anything but empty or `0` keeps it always. `<workspace>/sets/notices.json` remembers the one-time Shazam notice. The recognizer is `DJLIB_RECOGNIZER` (default `shazam`) or the request's `recognizer`; AudD needs `DJLIB_AUDD_TOKEN`, ACRCloud `DJLIB_ACRCLOUD_HOST`, `DJLIB_ACRCLOUD_KEY` and `DJLIB_ACRCLOUD_SECRET`, all read from the service's environment.

`djlib identify URL [--tracklist FILE]… [--again] [--recognizer shazam|audd|acrcloud] [--name NAME]` submits with a fresh key and follows the job: a live line in a terminal; with JSON output, stderr events `{"event": "identify_started", "job_id", "url"}` and `{"event": "identify_progress", "job_id", "phase", …progress}` at each phase change and at most every 15 s, ending with phase `completed` or `failed`. Ctrl-C cancels the job and exits 130 with `JOB_CANCELLED` (`details.job_id`); what was heard and downloaded stays, so running the command again continues; a failure exits 2 with the job's error code and `details.job_id`. The result is `job_id`, `source`, `recognizer`, `duration` (`mm:ss`, or `h:mm:ss` from an hour), `coverage` (`duration_seconds`, `seconds_identified`, `percent` named, `seconds_heard`, `percent_heard`, `gaps[]` of `{start, end}` not heard), `counts` (`tracks` plus the statuses; since 0.1.0a16 also `heard`, named tracks with audio evidence, `listed_only`, the other named tracks, and `ids`, the unknown ones), `tracks[]` (`n`, `start` `mm:ss`, `approx`, `kind` `named`|`unknown`, `artist`, `title`, `version`, `status`, one-line `evidence`, up to three `candidates`: `{source: "audio", label, artist, title, version, heard_by, windows, at, strength}`, `{source: "comments", label, …, mentions, likes, at}` or, for a conflict, `{source: LISTING, label, …, listed_in}`; since 0.1.0a16 `listen_url`), `unplaced[]` (up to 20 `{label, heard_by, at}`; since 0.1.0a16 `listen_url`), `sources`, `listed`, `mixesdb` (null, or `page_title`, `page_url`, `tracklist`, `match` of the MixesDB page merged), `tracklist_file`, `tracklist_json`, `reused`, `listened_at` (since 0.1.0a16: when the set was listened to, kept when the result is reused), `notices`, `publisher_text` (which fields quote untrusted text) and `next` (since 0.1.0a16 `djlib set URL --no-rekordbox`, which makes no rekordbox playlist, plus `djlib identify URL --tracklist paste` while IDs, `weak` or `conflict` tracks are left or under 70% is named, unless a tracklist was given: a `1001tracklists` or `file` source, or a `mixesdb` source without `page_url`, since a MixesDB page djlib looked up itself names its `page_url`; URLs are quoted for the shell). `listen_url` is the set's link at that moment (`https://www.youtube.com/watch?v=ID&t=Ns` or `https://soundcloud.com/PATH#t=m:ss`), only for https YouTube and SoundCloud links, else null. `warnings` holds the notices, then the skipped lines (quoted, cut to 160 characters). `djlib_identify_set` (`url`, `idempotency_key`, `tracklist_text`, `tracklist_source` default `file` since 0.1.0a16, was `1001tracklists`, lowercased, `again`) posts the same request and, since 0.1.0a16, answers a repeated key whose job has its tracklist with the same summary as `djlib_job`; `djlib_job` on a finished identify job returns that result without `job_id`, plus `skipped_lines` and `identified_at` (the raw tracklist stays in `tracklist_json`).

### Shazam history

`djlib set shazam[:SPEC]` reads the user's Shazam history in the CLI process and builds a request list in the order heard (artist, title, the mix as the version, the Shazam time and place in `notes`), keyed `shazam:<digest>`, then runs the `set FILE` steps; the result adds `shazam` (`name`, `description`, `sources`, `since`, `new`, `songs`, `songs_in_history`, `first_shazamed_at`, `newest_shazamed_at`, `left_out`, `remaining`) and `source.provider: "Shazam"`. Without SPEC it reads this Mac's Music Recognition history (`~/Library/Application Support/com.apple.shazamd/ShazamLibrary.sqlite`, which holds the iPhone's Shazams when Shazam syncs with iCloud) and the older Shazam app for Mac; SPEC is `new` (after the newest Shazam a previous import from this Mac took, remembered in `<workspace>/shazam.json` once every step of the set got through), a date (`2026-10-01`), `apple-music` (Music's “My Shazam Tracks”, read through JavaScript for Automation) or a path (an iPhone backup folder or the Backup folder, a `.sqlite`, or a `.csv`/`.txt`/`.tsv` export). Databases are copied with their write-ahead log and opened read-only. Records merge by ISRC or equivalent labels; a list holds 1,000 songs (the oldest from this Mac; the newest from a file or Apple Music). Since 0.1.0a16 `result.shazam.next_spec` is the `set` argument that brings the `remaining` songs: `shazam:new`, or `shazam:YYYY-MM-DD` (the list's last day) when a newer import already moved the `shazam:new` mark, or null. Lists are named after their days (`Shazam 26 Sep – 12 Oct`, with the year when it isn't this year) or their source (`Shazam (shazamlibrary.csv)`, `Shazam (iPhone backup)`), so an a15 Shazam set checked again gets a new list under the new name; notes keep place names but no bare coordinates, and date-only times have no ` 00:00`. `<workspace>/shazam.json` `last_import` gains `collection_id`, `newest_list` (`{name, request_id, collection_id}`, the import holding the newest Shazams) and `pending` (`{spec, songs, since}` or null: the rest of a list cut at 1,000 that `shazam:new` can't bring, kept until an import reads from that day or earlier); state files from 0.1.0a15 have none of them and every reader falls back. Errors: `SHAZAM_HISTORY_NOT_FOUND` (`details.setup`, `details.alternatives`; since 0.1.0a16 `next` `djlib shazam status`), `SHAZAM_ACCESS_DENIED` (Full Disk Access; since 0.1.0a16 `details.next` is `open "x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles"`), `SHAZAM_NOTHING_NEW` (`details.since`, `songs_in_history`, `last_import` with `collection_id`; since 0.1.0a16 `headline`, and `next`/`next_label`: the crate holding the newest Shazams, else that list, or `djlib shazam list` after a date with nothing new; the message no longer names a command, and the terminal shows it calmly, still with exit 2), `SHAZAM_BACKUP_ENCRYPTED`, `SHAZAM_HISTORY_UNREADABLE`, `SHAZAM_MUSIC_NOT_ALLOWED`, `SHAZAM_PLAYLIST_NOT_FOUND`, `SHAZAM_MUSIC_UNSUPPORTED` (Apple Music outside macOS), `SHAZAM_MUSIC_FAILED` (Music didn't answer, retryable, or its answer couldn't be read). `djlib shazam status` (also `djlib shazam` alone) lists the sources, songs, newest Shazam, last import and new songs since, with the setup steps when nothing is found; when Full Disk Access is what's missing it returns `setup: []`, `alternatives: []` and `new_since_last_import: null` and shows that instead. Since 0.1.0a16 its result adds `recent_spec` (`shazam:YYYY-MM-DD` for the last 30 days, or the 30 days before an older newest Shazam; null without history), and for a history of more than 100 songs with no import it suggests that first. `djlib shazam list [--since DATE|new] [--from apple-music|PATH] [--limit N]` and the read-only MCP tool `djlib_shazam_history` (`source`, `since`, `limit` 1–1000, run in the MCP process; no workspace needed) return `spec`, `query`, `songs`, `songs_in_history`, `since`, `new`, `sources`, `problems`, `newest_shazamed_at`, `recent_spec` (null with `--since` or `--from`) and `records`, newest first by `last_shazamed_at` (falling back to `shazamed_at`; 0.1.0a15 sorted by the first Shazam).

`set FILE` composes the headline workflow. It parses the tracklist like `requests create --text` (the same idempotency key, so rerunning an unchanged file reuses the list), hash-checks matches, then, if anything is owned, queues `requests collect` for the current revision, prepares the M3U8 and imports it into rekordbox unless a playlist of that name exists. With `--usb` it then runs the `rekordbox usb` flow for that crate. The result lists `name`, `request_id`, `revision`, `songs`, `owned`, `missing` (each `position`, `label`, `state`, `you_own` other versions), `collection_id`, `playlist`, `rekordbox` (`status`, `rekordbox_ui_seconds`, `verified_by`), `usb` (the `rekordbox usb` fields, or null) and `database_modified_directly: false`. With nothing owned, no crate or playlist is made and those fields are null.

Since 0.1.0a16 every `set` result (file, paste, link, Shazam) also has `tracks`, every item in set order, and `other_mix`, the number of tracks whose `own` is `other_mix`; `missing` and `owned_to_check` are unchanged. Each track has `position`, `timestamp`, `label` (an ID's `ID - ID` label is `ID`; `missing[]` keeps the old label), `artist`, `title`, `version` (null for IDs), `state`, `own` (`owned` for `satisfied`, `ambiguous` or `unavailable`, since the library holds that exact mix; `id` for an unknown item; `other_mix` for a named item with a `different_version` candidate; else `missing`, `source_selected` included), `in_crate` (true only for `satisfied`), `confidence`, `you_own`, `notes`, `matched_as` (below), `listen_url` (as for `identify`, null without a YouTube or SoundCloud link) and `shop` (null unless `own` is `missing` or `other_mix`: `{beatport, bandcamp, traxsource}` search URLs for artist, title and version, without “(Original Mix)”, featured credits or a trailing `[LABEL]`, query encoded with `+` for spaces); IDs add `maybe`, what djlib heard there or null, never the ID's name. With `--no-rekordbox`, `rekordbox` (status `skipped`, `reason_code: NOT_REQUESTED`) adds `installed`, whether the rekordbox app is on this Mac. A `.csv` or `.tsv` FILE whose first line is `Shazam Library` or that has a Shazam-only column (`TagTime`, `TrackKey`, `ShazamKey`, `ShazamID`) is read as `shazam:FILE`, unless `--source`, `--identify` or `--tracklist` is given; any other CSV or TSV with Artist and Title columns, and pasted tab-separated text with that header row, is a song list (named after the file, or as a paste; no `shazam` key; a Mix, Version or Remix column sets the version exactly).

The CLI's `set` commands and `requests create` post `POST /requests?same_list=true` (the default is false, so MCP `djlib_create_request` and other API callers keep plain key replay). When the key is new, `same_list` looks for the newest saved list with the same `name` and the same songs in the same order (a song is its normalized artist, title and version; an ID counts only by its position; notes, times, links, `also` and `confidence` are evidence). If there is one, its items' inputs are replaced in place (the revision goes up only when something changed; item IDs, resolutions and source selections are kept), the new key is registered to it, and it comes back with `reused: true`. Crates are keyed by the list and its owned tracks, so an unchanged owned set keeps its crate and rekordbox playlist. A list holding only IDs is never found by name, only by its key. This is how a set checked with 0.1.0a15, whose notes and so whose key differ, is updated rather than duplicated; a set whose songs or name changed (untimed IDs now kept, a Shazam list's new name, a paste on another day) is a new list, and one with more owned songs gets a new crate.

`AnalysisImport.path` is optional. Without it, the coordinator reads rekordbox's analysis folder (macOS `~/Library/Pioneer/rekordbox/share/PIONEER/USBANLZ`, Windows `%APPDATA%\Pioneer\rekordbox\share\PIONEER\USBANLZ`), parsing only files whose size or modification time changed. Each `ANLZ0000.DAT` contributes its file name, median beat-grid tempo and hot/memory cue counts; a track matches only when exactly one catalog recording has that file name (originals or prepared working copies), and the newest analysis per name wins. BPM is stored like XML values (`rekordbox_analysis`, unverified, never replacing other sources) and cue counts under the annotation key `rekordbox`. Key is not included (`key_included: false`). Once a workspace has synced, the coordinator repeats the sync every two minutes. `NATIVE_ANALYSIS_UNAVAILABLE` means no analysis folder exists.

Scans label untagged files from their names (`03 - Artist - Title (Mix)` → artist and title) while keeping provisional byte identity (`identity_evidence.labels_source: file_name`); a rescan relabels an earlier `Unknown artist` provisional recording without changing its identity or memberships. Request matching also considers provisional recordings whose labels are equivalent, reported as `identity_match: file_name_labels`.

The default workspace is `DJLIB_WORKSPACE`, else the path remembered by `djlib use PATH` (the first successful `init` remembers itself when nothing is set), else `~/.local/share/djlib/default`. `GET /summary` returns `tracks`, `with_bpm`, `with_key`, `rekordbox_analysis_synced_at`, `collections`, `request_lists`, `deliveries`, `active_jobs`, and the five most recent collections and request lists (`owned`, `missing`, `unresolved`, `needs_check`); `djlib status` adds `in_rekordbox` per collection when rekordbox can be read without focusing it, `rekordbox_checked`, and `service_url`. Since 0.1.0a16, `recent_requests[]` rows add `counts` and `recent_collections[]` rows add `request_id` (the list the crate was collected from, read from its collect job's key, or null), so status shows each crate on its own set's line; `owned` there is still the `satisfied` count. `djlib status` adds `rekordbox_app` (the rekordbox app is installed, so macOS), `rekordbox_open` (only when `rekordbox_app` is true and the playlists couldn't be read: whether rekordbox is running, or null) and `shazam_history_found` (this Mac's Music Recognition database exists; one stat, nothing opened). `GET /requests` rows (`requests list`, MCP `djlib_requests`) add `counts` `{owned, missing, other_mix, ids}`, which always add up to `total_items`: `owned` is `satisfied`, `ambiguous` or `unavailable` (as `own` in `set` `tracks`), `ids` other unknown items, `other_mix` other named items with a `different_version` candidate, `missing` the rest. Only `satisfied` items go into a crate.

A coordinator started implicitly by a command is launched with `--idle-exit 1800` and exits after 30 minutes without requests or queued/running jobs; `service start` launches one without idle exit.

`delivery plan` also accepts `--collection ID` (repeatable), `--workflow`, `--app-version`, optional `--name`, `--player` and `--full` instead of `--file`.

Named request items preserve artist/title/version; unknown items retain a label, with a timestamp and HTTPS source as optional evidence (0.1.0a15 required one of them), and no guessed identity, other spelling or `also`. Since 0.1.0a16 a named item may carry `also`: at most one `{artist (1–500), title (1–1000), version (≤300, default ""), source (≤40, default "")}`, another spelling of the same song's credits. `djlib set LINK` adds it only for a `confirmed` track whose shown label took the audio's spelling over a listing's (`also_named`): the listing's artist with the shown title and mix (the listing's own title and mix only when they are the same), never for likely, weak, conflict or unidentified tracks. Only when the item's own labels match no file is `also` checked, by the same exact rule (versions are never loosened): one verified match satisfies the item with `accepted.basis: exact_catalog_labels` plus `accepted.matched_as` (the spelling's “Artist - Title (Version)”) and `accepted.matched_as_source`; two or more make it `ambiguous`, and `requests resolve` accepts a recording matching either spelling (`operator_selection` keeps `matched_as`); `different_version` matches join `candidates`. An empty `also` is left out of stored inputs and keys, so lists without it serialize exactly as in 0.1.0a15. `requests get` items in the CLI's JSON add `shop` for songs not owned. Saved reads are paginated snapshots (`next_offset` maps to `after`); explicit create/refresh/resolution performs bounded checks. Source selection is separate from acquisition. Multiple exact byte revisions require explicit selection. See [request recipes](../skills/dj-library/references/requests.md).

Annotations bind exact recording/revision IDs. Revision `0` creates the first annotation; later patches require the current revision. Omitted fields are unchanged and explicit null clears the annotation. BPM/key values carry `source: operator|native_tag` and `verified: false` by default; `native_tag` must match freshly read catalog tags. Organization freezes ordered collections from up to 1,000 explicit references, reports exclusions and uses explicit unknown policies. It does not perform acoustic analysis or retag catalog originals. See [organization recipes](../skills/dj-library/references/organize.md).

## Bounds and paging

- Job/item/library limits: 1–100; defaults 20. Collection default 50, maximum 100.
- Collection `after` is a zero-based offset; initial value 0.
- Items `after` is the last position returned; initial value -1.
- Events `after` is the last event cursor returned; initial value 0.
- `next_cursor: null` ends a collection/item/event page.
- Queries match every word, ignoring case and accents (“bjork radio” finds “Björk … (Radio Edit)”). Library rows are ordered by artist, title, version, then IDs; saved lists newest first. Job queries also match the job kind.
- Library, jobs and saved collection/request/delivery lists accept a query and opaque `after` cursor. Reuse `next_cursor` with the same listing/query; a null cursor ends paging. Results include total and an insertion cutoff, with current mutable metadata/locations. Library groups each recording/revision and all recorded locations; availability is not freshly checked. Reviews remain a bounded view without a continuation cursor.
- Plan replies include a ten-track preview; full input is persisted privately.
- Source descriptions are limited to 30,000 characters and chapters to 500; output declares description truncation.
- An identification takes up to five tracklists of up to 200,000 characters each; its result keeps up to 50 skipped lines, and the compact result (CLI, `djlib_job`) up to 20 unplaced songs and three candidates per track.
- Current collection cap: 10,000 local tracks; selected URL download cap: 1,000 tracks; up to 100,000 music files per scan (`ITEM_LIMIT` beyond that).

## Exit and outcome semantics

| Exit | Meaning |
| --- | --- |
| 0 | Command succeeded or job intent accepted; acceptance does not imply completion. |
| 2 | Invalid input or application error; inspect the envelope. |
| 3 | `jobs wait` deadline reached; job continues in the coordinator. |
| 4 | `jobs wait`/`watch` returned failure, cancellation, a pause, required attention, or completion with gaps. |
| 130 | Interrupted in a terminal (Ctrl-C); accepted jobs keep running, except that `identify` and a listening `set` cancel their identification (`JOB_CANCELLED`); running them again continues from the saved windows. |

`jobs wait` is a convenience with a maximum 60-second polling window; `jobs watch` waits until the job leaves queued/running. In a terminal, submissions that follow their job use the same exit codes. MCP clients should poll `djlib_job` and respect `next_poll_after_seconds` (15 or 30 seconds for a listen, 2 for other running jobs). To inspect all items in a bulk job, page through outcomes instead of repeatedly loading the whole input.

## Recovery and readiness

`TRANSPORT_UNCERTAIN` means a mutation may have been accepted. For keyed submissions, resubmit the identical request with its original idempotency key. `IDEMPOTENCY_CONFLICT` means the key belongs to another intent. One opt-in exception: `POST /requests?same_list=true`, which the CLI's `set` and `requests create` use, registers a new key to the newest list with the same name and songs and updates that list in place (see `set FILE` above); without the parameter, keys behave as before. `PLAN_STALE`, `REVIEW_STALE`, and `DELIVERY_STALE` require reading the latest state before choosing another action.

Startup is a separate boundary: `SERVICE_START_BUSY` means the startup lock timed out; `SERVICE_START_FAILED` means the child exited without a discovered healthy service; `SERVICE_START_TIMEOUT` means the child was still running after the readiness window. These errors submit no music operation. Read `service status` and the indicated log before retrying, especially on timeout. Windows MCP `COORDINATOR_START_REQUIRED` requires external-terminal `service start` or the generated launcher, not another cold-start MCP call.

Delivery planning creates a new frozen delivery record on each call; it has no idempotency-key field. Preparation is keyed: intent, the delivery-to-job binding, and items are committed before media work. Concurrent preparation requests for the same frozen delivery share one job, including requests with different fresh keys; each key is bound to that job. A key already naming another request returns `IDEMPOTENCY_CONFLICT`; a different preparation payload for an already-bound delivery returns `DELIVERY_CONFLICT`.

Organization and catalog reconciliation return durable jobs; supplied keys replay the original intent. Passed `analyzed` and `native_exported` observations plus `verify-app` also return jobs, deriving an idempotency key from delivery ID, revision, operation and full observation. Repeating the same intent returns the same job after a lost response; use the latest revision for a new check. Other observations, device binding and device verification remain direct revision-checked operations. Evidence updates use atomic compare-and-swap; deferred job finalizers also fence against stale generations and paused/cancelled work. Inspect failed items and reread delivery evidence after a failure, since failure invalidation can advance the revision.

A completed verification job returns only `delivery_id`, `revision` and `evidence_committed: true`. It never returns `ready_for_app_use`. Read the delivery for `app_requirements_met_at_last_check`, `evidence.app_readback.checked_at` (also `last_app_readback_at`) and blockers. These are saved evidence, conditional on operator-reported app behavior. Use the current delivery revision to submit a new check when freshness matters. Passed native-export observations verify exact analyzed bytes per item and bound-volume identity at acceptance/finalization; they do not perform the native export.

Exports report `app_state: prepared_for_import` and `device_state: not_exported`. Generic collection replies use `not_tracked_here`; they do not infer either native success or failure. Delivery evidence is separate. A delivery with partial preparation publishes no native import handoff. Neither preparation nor native-library filenames establish app import, native export, or playback.

`delivery get` combines historical observations/readback with a current lightweight volume-identity and marker check. Its `requirements_met_at_last_check` may be true, but `hashes_rechecked_by_status` is false and `ready_for_departure` remains false. `last_audio_readback_at` identifies the stored readback time. Only `delivery verify-device` can return `ready_for_departure: true`, after fresh matching audio hashes and all native, device, and hardware requirements pass. This is attributed operator evidence plus machine byte readback, not automatic player verification: `hardware_verified_automatically` and `native_automation_available` remain false.

Rebinding a device invalidates device-dependent evidence. Re-observing an earlier stage invalidates later stages; detected changes to or loss of analyzed working files invalidate analysis and subsequent readiness. Readback checks do not write the USB or interpret native database contents. See [the delivery workflow](DJ_DELIVERY.md) for the supported app steps and remaining hardware boundary.
